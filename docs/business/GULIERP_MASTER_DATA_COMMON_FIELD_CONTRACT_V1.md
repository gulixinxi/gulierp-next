## 1. Purpose

This contract freezes the V1 common-field policy for GuliERP master data. It is intended to constrain later database, Entity, DTO, API, UI and test work without forcing every aggregate into one generic master-data engine.

The contract answers which fields are truly common, which fields are entity-specific, how scope and lifecycle are expressed, and how future remediation should remain additive and ERP-oriented.

| `OPTIONAL` | The field may exist, but is not required by the V1 contract. |

## 4. Master Data vs Reference Data

`MASTER_DATA` is operator-maintained business identity used by transactions, permissions, logistics or organization workflows. Examples: BusinessPartner, Item, Warehouse, Employee.

`REFERENCE_DATA` is a controlled vocabulary or standard catalogue. It may have Code and Name, but it is not a business actor or owned operational object. Examples: UOM, DictionaryType, DictionaryItem, PaymentMethod.

`CONFIGURATION` controls system behavior. It must not be forced into the same common-field contract as business master data. NumberingRule is configuration for document numbering management, not a master-data object.

`TRANSACTION_DATA` is excluded from this contract. Sales orders, purchase orders, inventory documents and receiving flows are outside this goal.

## 5. Scope Model

GuliERP V1 uses scope as domain semantics, not a fixed TenantId + CompanyId pair on every table.

| Scope type | Meaning |
|---|---|
| `TENANT` | Owned by one tenant and visible across companies in that tenant. |
| `COMPANY` | Owned inside one tenant and one company. |
| `ORGANIZATION` | Owned inside a company organization tree or department. |
| `GLOBAL_REFERENCE` | Shared system reference data without TenantId. |
| `CONFIGURATION_SCOPE` | Operational configuration, scoped as required by the owning module. |

TenantId is required for tenant-owned business master data. CompanyId is required only for company-scoped objects. OrganizationId is not a generic master-data field; it appears only where the business object is truly organization-scoped.

## 7. ID Contract

`Id` is the unified technical primary key for persisted master/reference/configuration rows. It is not operator-visible identity and must not replace Code in business communication.

V1 uses `long` technical ids. Client create and update DTOs must not accept Id except as route or relationship reference. Id is stable after creation and never changed.

## 8. Code Contract

Code is the stable business identifier for first-class master data and controlled reference data.

Frozen Code rules:

| Rule | Contract |
|---|---|
| Required | Yes for BusinessPartner, Item, ItemCategory, UOM, Warehouse, Location, Company, OrganizationUnit/Department, Plant; Employee uses EmployeeNo as its Code equivalent. |
| Max length | 40 characters. |
| Trim | Server must trim. |
| Whitespace | Not allowed in canonical Code. |
| Chinese characters | Not allowed in canonical Code. Name carries Unicode display text. |
| Case | Canonical uppercase. Comparisons are semantically case-insensitive through normalization to uppercase. |
| NormalizedCode | Not required as a separate V1 persisted field if Code is stored canonical uppercase. |
| Format | Current V1 evidence uses `^[A-Z][A-Z0-9_]{1,39}$`; downstream code-rule goal may refine validators without widening semantics casually. |
| External interfaces | Code may appear in imports, exports, printed labels, selectors and document snapshots. |
| Business documents | Documents may snapshot Code; changing Code after references exist is therefore controlled. |
| API create Code | Required in current manual mode. Future auto-code compatibility should allow create Code to become nullable only through a versioned DTO or explicit generation mode. |
| Manual input | Allowed in V1. |
| System generation | Allowed only after `GULIERP_MASTER_DATA_CODE_RULE_STANDARD_V1`; not implemented by this contract. |

This goal freezes Code field semantics only. It does not freeze prefix DSL, sequence tables, reset algorithms, reservation, preview API or concurrency implementation for auto-code generation.

| Entity | Current behavior | V1 policy | Rationale |
|---|---|---|---|
| BusinessPartner.Code | create-only DTO | `CONTROLLED_CHANGE` | Partner codes can be referenced by documents and operators; correction should require explicit permission, no duplicate, audit trail and warning. |

## 12. Alias / SearchKeywords Decision

V1 decision:

| Field | V1 decision | Rationale |
|---|---|---|
| Alias | Do not add a universal persisted Alias field in V1. For BusinessPartner and Item, defer a governed alias model to a later search/alias goal. |
| SearchKeywords | Do not add a universal persisted SearchKeywords field in V1. Expand default search over explicit fields first. |

BusinessPartner and Item need better search now, but a free keyword bag adds maintenance cost, unclear ownership, index cost and API complexity. V1 should first add MnemonicCode where valuable and expand default keyword search to known fields such as contact, phone, tax number and specification.

If alias is later adopted, it should be modeled deliberately, likely as a child table for BusinessPartner/Item rather than a comma-separated common field.

## 13. Status Contract

V1 master data status model is Active / Inactive for MDM-owned master/reference data.

| Rule | Contract |
|---|---|
| Default on create | Active. |
| Active | Can be selected for new business documents and operational references. |
| Inactive | Preserved for history; not selectable by default for new documents. |
| Delete distinction | Inactive is not deletion. It blocks new selection while preserving references. |
| API list | Admin lists may include status filter and support all statuses. |
| Selector APIs | Default to Active only unless caller asks for inactive rows. |
| Historical documents | Continue to display snapshots/references even if master data becomes inactive. |
| Rich lifecycle | Draft, Approved, Frozen, Archived and Deleted are not part of MDM V1. |

Identity-adjacent entities keep their existing richer enums where domain semantics require them:

| Entity | Status enum | Contract note |
|---|---|---|
| Company | Active, Suspended, Closed | Legal entity lifecycle remains Identity-owned. |
| Plant | Active, Inactive, UnderConstruction, Decommissioned | Plant lifecycle is site-specific. |
| OrganizationUnit | Active, Inactive, Archived | Organization tree lifecycle remains Identity-owned. |
| Employee | Active, Inactive, Left | Employee has HR-lite lifecycle. |

## 14. Description / Remark Contract

V1 standard field name is `Description` for optional free-text context on master/reference data.

`Remark`, `Note` and `Comments` should not be introduced for the same generic meaning. They are allowed only when a domain has a distinct business meaning. Current MDM entities use Description, so later MDM remediation should keep Description.

Description max length is 2000 where current MDM configuration already uses that limit.

## 15. Audit Contract

V1 audit fields are required for persisted master/reference/configuration rows:

| Field | Contract |
|---|---|
| CreatedAt | Application-generated server timestamp at create. |
| CreatedBy | Application context user id when available; nullable for seed/system operations. |
| ModifiedAt | Application-generated server timestamp at create and every update. |
| ModifiedBy | Application context user id when available; nullable for seed/system operations. |

Current project evidence uses `CreatedAt`, `CreatedBy`, `ModifiedAt`, `ModifiedBy` on MDM and Identity entities. `NumberingRuleDto` exposes `UpdatedAt`, but the entity uses `UpdatedAt` rather than `ModifiedAt`; that is a local inconsistency to handle in a later compatibility step, not a reason to rename all MDM audit fields now.

Create/update DTOs must not allow clients to submit audit values. Read DTOs should expose CreatedAt and ModifiedAt by default. Detail views may expose CreatedBy and ModifiedBy when user display resolution exists. Lists should default to ModifiedAt for operator recency.

Timestamps are `DateTimeOffset`; application code currently uses UTC generation in services. V1 continues server-generated UTC-oriented timestamps.

## 16. Concurrency Contract

V1 requires `ConcurrencyVersion` for first-class mutable master/reference/configuration rows. Current MDM and Identity evidence marks it as EF Core concurrency token and update DTOs carry `ExpectedConcurrencyVersion`.

RowVersion, PostgreSQL xmin and timestamp-based optimistic locks are not required for V1. The common contract is the integer `ConcurrencyVersion`, incremented by the application service on update.

## 17. Delete Contract

V1 deletion model is `Never delete when business-referenced; deactivate instead`.

| Entity | Delete policy | Rationale |
|---|---|---|
| BusinessPartner | `INACTIVE_ONLY` | Customers/suppliers are referenced by documents. |
| Item | `INACTIVE_ONLY` | Items are referenced by sales, purchase and future inventory. |
| ItemCategory | `INACTIVE_PREFERRED` | Category tree and item references should be preserved. |
| UOM | `INACTIVE_ONLY` | Unit references must remain stable. |
| Warehouse | `INACTIVE_ONLY` | Logistics history and locations must remain stable. |
| Location | `INACTIVE_ONLY` | Printed labels and inventory history require preservation. |
| DictionaryType | `SYSTEM_PROTECTED_OR_INACTIVE` | System dictionaries cannot be casually deleted. |
| DictionaryItem | `SYSTEM_PROTECTED_OR_INACTIVE` | Tenant items may be retired, system items protected. |
| PaymentMethod | `INACTIVE_ONLY` through dictionary item | Sales references payment methods. |
| NumberingRule | `INACTIVE_ONLY` | Configuration history should remain auditable. |
| Company | `CLOSED_OR_SUSPENDED` | Legal entity history is preserved. |
| OrganizationUnit / Department | `INACTIVE_OR_ARCHIVED` | Organization history is preserved. |
| Employee | `INACTIVE_OR_LEFT` | Employment history is preserved. |
| Plant | `INACTIVE_OR_DECOMMISSIONED` | Site history is preserved. |

Soft-delete columns such as IsDeleted, DeletedAt and DeletedBy are not common V1 fields.

No current decision requires destructive migration. Preferred strategy is additive, nullable first, then backfill and validate.

## 29. Migration Principles

1. Prefer additive migrations with nullable fields first.
2. Preserve existing Code values.
3. Preserve current text address fields during structured-address transition.
4. Do not reuse DocumentKernel counters for master-data Code generation.
5. Do not rename audit fields broadly; adapt compatibility at boundaries.
6. Add indexes only for fields that enter default search.
7. Expand DTOs compatibly or version them when a create field such as Code becomes nullable under auto-code mode.
8. Never introduce a universal master-data table or low-code metadata layer as part of this contract.

## 30. Non-Goals

This contract does not implement:

- production code changes;
- database changes;
- migrations;
- DTO/API/frontend/test changes;
- BusinessPartner remediation;
- Item remediation;
- Warehouse or Location remediation;
- code-rule generator;
- country or administrative-region imports;
- purchase, sales or inventory receiving features;
- universal master-data engine;
- dynamic entity engine;
- metadata-driven CRUD platform;
- generic search DSL;
- global schema registry.
