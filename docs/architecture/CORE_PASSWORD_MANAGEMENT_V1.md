# Core 密码管理 V1

## 适用范围

ERP 与 CRM 共用 Identity Core 的本地账号、密码哈希、Cookie 会话和密码策略。CRM 不维护第二份账号或密码。现有账号的密码哈希继续有效；新策略只在设置新密码时生效。

## 已实现

- 新密码长度为 15–128 个字符，不强制大小写、数字或特殊字符组合；拒绝少量已知弱密码、包含 `changeme` 或包含用户名的密码。当前内置名单只是基础拦截，不等于完整的已泄露密码库。
- 用户菜单中的“修改密码”要求当前密码、新密码及确认输入。`POST /api/v1/auth/password/change` 要求已登录和有效 CSRF 令牌，并限制每个用户 15 分钟内最多 10 次请求。接口不返回密码。
- 修改成功后当前浏览器退出登录，其他 Cookie 会话由安全戳校验失效；校验间隔最长 1 分钟。旧密码不再可登录。
- 新开发库首次播种时，操作员须分别提供 `GULIERP_DEV_SEED_PLATFORM_ADMIN_PASSWORD` 和 `GULIERP_DEV_SEED_TENANT_ADMIN_PASSWORD`，两者必须不同且满足新策略。缺少时播种在写入前失败。已有数据库不会自动改密。
- 身份初始化工具中会设置密码的路径复用 Core 策略；只读诊断路径不变。

## 操作要求

在安全的本地环境注入两个播种环境变量，不要把值写入 `.env.example`、源码、提交、日志或工单。生产环境使用单独的凭据管理渠道。密码不应由管理员通过聊天工具传递。启动已有数据库无需设置播种密码；不要为了更新密码而重新播种或运行迁移。

## 后续阶段

1. 管理员辅助重置：确定身份核验、最小权限、一次性重置凭证的交付渠道和审计事件后实现。
2. 首次登录改密及历史弱密码治理：为既有账号设计标记、宽限期和无障碍恢复流程。
3. 完整的已泄露密码拦截、MFA 与凭据托管：选择可维护的数据源和认证器，再在测试环境验证。

这些阶段尚未实现，不应作为当前系统已经具备的能力对外宣称。
