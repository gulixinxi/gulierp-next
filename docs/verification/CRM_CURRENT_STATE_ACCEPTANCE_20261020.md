## 本轮发现和处理的阻断项

### P0：登录票据定时刷新后丢失租户与公司范围

现象：重新登录后组织和 CRM 页面短时可用；随后读取 API 返回 403，刷新页面变成未登录。先前容易被误判为启动方式或数据库环境问题。

原因：Identity 安全戳校验成功后会重建 `ClaimsPrincipal`。登录时通过 `SignInWithClaimsAsync` 加入的租户、公司、显示名和平台管理员范围没有自动带入重建后的票据。`AuthenticationContextMiddleware` 因此无法得到当前租户/公司，按公司授权的接口被拒绝。

处理：在安全戳校验的 principal 刷新回调中，从已验证的旧票据保留租户、公司和显示名，并依据当前用户及有效角色重新计算平台管理员权限；保留每分钟安全戳校验。新增零间隔集成测试，先复现失败，再验证默认公司、CRM 读取权限、切换公司后的权限均保留。修复版服务跨过校验周期后，组织页面与 CRM 页面读取仍可用。

### P1：主业务闭环缺少可执行验收条件

测试库中 CRM 业务表为空，当前验收账号只有 CRM 读取权限。不能把“页面能打开”写成“线索→客户→跟进→商机”通过。下一步应使用隔离的测试宿主/测试账号与可回收测试数据，按最小路径逐项验证创建、转化、跟进、阶段推进及失败回滚；不得扩大当前只读账号权限来绕过验证条件。

### P2：看板错误状态不明显

看板请求失败时统计位显示 `-`，主要错误进入控制台；在本轮票据失效期间，页面表面上接近空数据。后续应区分“加载中、真实零数据、请求失败”，避免错误被当作业务无数据。

## 下一段验收顺序

1. 建立隔离的 CRM 写入测试身份或测试宿主，不改变现有 `CRM_READONLY` 权限；准备标记明确的测试数据。
2. 验证线索创建→认领/分配→跟进→转为 `crm.Company`→联系人→商机→赢/输单，逐步补回归测试与失败场景。
3. 再验收看板、今日待办、建议、情报信号与导入日志的数据一致性；之后才进入报价与 ERP 交接设计。
